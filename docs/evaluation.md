# 実API・文章品質の評価

初期開発時はAPIキー未設定で、後に架空原稿による実API疎通を1回確認した。文章品質の優位性は未測定。テストに登場する改稿は架空原稿から人為的に作ったfixtureで、Sarashinaの実出力ではない。

## 初回疎通

キー設定後 `node scripts/live-smoke.mjs --live` を実行。架空の学術原稿を1回送信して2候補を取得する。401/429/通信エラーは失敗として扱う。成功時の候補、finish_reason、使用トークン、機械検査を確認する。このコマンドにホストの意味審査は含まれない。

## アプリからの実用確認

1. 新しいチャットでSarashina Editorを選び、例文を編集依頼する。
2. status、begin、proposeが実際に呼ばれ、キーが会話に出ないことを確認。
3. 読み手・用途・用語集・主張の限定が編集方針に含まれることを確認。
4. 候補に具体的指摘を返し、前の候補への再修正が行われることを確認。
5. reviewを通過する前に確定しないことと、finalizeの本文を再改稿せず提示することを確認。

## 品質比較

同じ入力と読者条件でA:ホスト単独、B:Sarashina単独、C:協働を作成する。比較者には生成元と順番を隠し、順番を無作為化する。美しさの軸は一律にせず、少なくとも以下の5用途を含める。

| 用途 | 読みやすさの基準 | 意味上の失敗例 |
|---|---|---|
| 論文 | 明晰な論証、自然な留保 | 相関を因果へ、示唆を実証へ |
| 技術文書 | 条件と動作の対応 | mayをmustへ、必要条件と十分条件の逆転 |
| 業務メール | 距離に合う敬意、明確な依頼 | 依頼を決定事項へ、期限変更 |
| 一般向け解説 | 自然な具体性、滑らかな接続 | 分かりやすさのために例や根拠を捏造 |
| 随筆 | 書き手の声、文の呼吸と余韻 | 語り手の気持ちや出来事を追加 |

正確さは合否と根拠箇所で判定し、失敗案を文体の点数で救済しない。合格した案だけについて「自然さ」「読者・用途への適合」「書き手らしさ」「冗長さ」を5段階で評定し、好みと理由も記録する。元原稿も比較対象に入れる。モデル自身の点数を人間の評価と混同しない。

小規模でも各用途3本以上を用意し、単発の好例で最適化を断言しない。セッション当たりの呼び出し回数、待ち時間、トークン数も記録する。推敲が長引くなら温度や往復数を増やす前に、元原稿・用語集・指摘の具体性を見直す。
